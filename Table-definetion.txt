# Life OS V1 — Complete Table Schema

## Core Concepts

The eight core concepts are:

```text
Task
Goal
Project
Idea
Philosophy
Workflow
Resource
Record
```

They are stored independently in:

```text
tasks
goals
projects
ideas
philosophies
workflows
resources
records
```

Supporting infrastructure:

```text
relations

labels
entity_labels

workflow_states
workflow_state_transitions

project_states
project_state_transitions

project_entity_states
```

There is:

```text
NO entities table
NO database foreign keys
```

All logical-reference validation is performed by the application/domain layer.

---

# 1. `tasks`

A Task defines:

> What should be done and what must be true when it is finished.

```text
tasks

id                  UUID PRIMARY KEY
                    // Globally unique Task identifier.

title               TEXT NOT NULL
                    // Short human-readable name.

description         TEXT
                    // Optional context or explanation.

target_description  TEXT NOT NULL
                    // Describes exactly what work should be performed
                    // and what result should be produced.

exit_criteria       TEXT
                    // Conditions that must be satisfied before the Task
                    // can be considered successfully finished.

priority            INTEGER
                    // Relative execution priority.
                    // Priority semantics are defined by the application.

created_at          DATETIME NOT NULL
                    // When the Task was created.

updated_at          DATETIME NOT NULL
                    // When intrinsic Task information was last modified.

archived_at         DATETIME
                    // When the Task was archived.
                    // NULL means not archived.
```

The Task table does not contain:

```text
state
status
labels

project_id
goal_id
workflow_id

deadline
budget
allocation
constraints

dependencies
resources
```

These belong to supporting tables, Relations, or Resource Relations.

---

# 2. `goals`

A Goal defines:

> A state we want to achieve.

```text
goals

id                UUID PRIMARY KEY
                  // Globally unique Goal identifier.

title             TEXT NOT NULL
                  // Human-readable Goal name.

description       TEXT
                  // Optional context or explanation.

target_state      TEXT NOT NULL
                  // Description of the desired future state.

success_criteria  TEXT
                  // Observable conditions that determine whether
                  // the desired state has actually been achieved.

created_at        DATETIME NOT NULL
                  // When the Goal was created.

updated_at        DATETIME NOT NULL
                  // When intrinsic Goal information was last changed.

archived_at       DATETIME
                  // When the Goal was archived.
```

State, labels, Project membership, Workflow, target date, Resources and constraints are external to this table.

---

# 3. `projects`

A Project defines:

> A context for managing related activity toward exactly one Goal (strict 1:1 pursuit).

```text
projects

id           UUID PRIMARY KEY
             // Globally unique Project identifier.

title        TEXT NOT NULL
             // Human-readable Project name.

description  TEXT
             // Optional detailed Project description.

purpose      TEXT
             // Explains why the Project exists and what it is
             // intended to manage or accomplish.

created_at   DATETIME NOT NULL
             // When the Project was created.

updated_at   DATETIME NOT NULL
             // When intrinsic Project information was last modified.

archived_at  DATETIME
             // When the Project was archived.
```

The Project's management Workflow is represented through `relations`.

Its own lifecycle can also be managed through the generalized Project State system.

---

# 4. `ideas`

An Idea defines:

> Something produced by thought and waiting for triage.

```text
ideas

id                UUID PRIMARY KEY
                  // Globally unique Idea identifier.

title             TEXT NOT NULL
                  // Short summary of the Idea.

description       TEXT
                  // Optional context.

idea_description  TEXT NOT NULL
                  // Actual content of the Idea.

captured_at       DATETIME NOT NULL
                  // When the Idea was originally captured.

created_at        DATETIME NOT NULL
                  // When it was stored in Life OS.

updated_at        DATETIME NOT NULL
                  // When intrinsic Idea information was last modified.

archived_at       DATETIME
                  // When the Idea was archived.
```

An Idea can receive Labels and participate in a State Machine just like other core concepts.

# 6. `workflows`

A Workflow defines:

> A reusable process describing how something should be performed or managed.

```text
workflows

id              UUID PRIMARY KEY
                // Globally unique Workflow identifier.

title           TEXT NOT NULL
                // Human-readable Workflow name.

description     TEXT
                // Detailed explanation of the Workflow.

workflow_type   TEXT NOT NULL
                // General purpose/category of this Workflow.
                //
                // Examples:
                // task_execution
                // goal_execution
                // project_management
                // idea_triage

purpose         TEXT
                // Explains what the Workflow is intended to accomplish.

version         INTEGER NOT NULL
                // Version number of this Workflow definition.

entry_criteria  TEXT
                // Conditions expected before applying/starting
                // the Workflow.

exit_criteria   TEXT
                // Conditions determining when the Workflow
                // has completed its purpose.

created_at      DATETIME NOT NULL
                // When this Workflow definition was created.

updated_at      DATETIME NOT NULL
                // When it was last modified.

archived_at     DATETIME
                // When the Workflow was archived.

supersedes_id   UUID
                // Logical reference (no foreign key) to the previous
                // published version of this definition. NULL for the
                // first version of a line.

published_at    DATETIME
                // When this version was published. Once set, the row's
                // definition is immutable; the next version is a new row
                // whose supersedes_id points here.
```

Each `workflows` row is one version of a definition. Publishing freezes a
version; successors form an explicit lineage chain through `supersedes_id`.

A Workflow may itself have Labels and be managed through a State Machine.

# 7. `resources`

A Resource defines:

> Something available that enables or constrains action.

```text
resources

id             UUID PRIMARY KEY
               // Globally unique Resource identifier.

title          TEXT NOT NULL
               // Human-readable Resource name.

description    TEXT
               // Optional Resource explanation.

resource_type  TEXT NOT NULL
               // Semantic Resource category.
               //
               // Examples:
               // time
               // money
               // attention
               // energy
               // token
               // compute
               // person
               // equipment

unit           TEXT
               // Measurement unit.
               //
               // Examples:
               // hour
               // JPY
               // token
               // GPU-hour

behavior       TEXT
               // Describes Resource behavior.
               //
               // Examples:
               // storable
               // perishable
               // renewable
               // reusable

capacity       DECIMAL
               // Optional capacity currently represented
               // by this Resource.

created_at     DATETIME NOT NULL
               // When the Resource was created.

updated_at     DATETIME NOT NULL
               // When its definition was last modified.

archived_at    DATETIME
               // When the Resource was archived.
```

Constraints are not intrinsic Resource or Entity fields.

They are represented through core `relations`.

# 8. `records`

A Record defines:

> Something that actually happened.

```text
records

id           UUID PRIMARY KEY
             // Globally unique Record identifier.

title        TEXT
             // Optional short summary of what happened.

description  TEXT NOT NULL
             // Human-readable description of the actual occurrence.

record_type  TEXT NOT NULL
             // Classification of the Record.
             //
             // Examples:
             // action
             // observation
             // progress
             // failure
             // discovery
             // state_transition
             // resource_usage
             // external_event
             // correction

occurred_at  DATETIME NOT NULL
             // When the thing actually happened.

recorded_at  DATETIME NOT NULL
             // When it was entered into Life OS.

actor        TEXT
             // Optional actor/source responsible for or reporting
             // the occurrence.

payload      JSON
             // Optional structured information specific to this Record.
             //
             // Examples:
             // transition information
             // measurements
             // external identifiers
             // execution details

created_at   DATETIME NOT NULL
             // When the database Record was created.

updated_at   DATETIME NOT NULL
             // When the Record was last corrected or updated.

archived_at  DATETIME
             // When the Record was archived.
```

Record relationships to Task, Goal, Project, Resource, etc. belong in `relations`.

# 9. `relations`

`relations` stores semantic relationships **only among core concepts**.

Allowed entity types:

```text
task
goal
project
idea
philosophy
workflow
resource
record
```

```text
relations

id             UUID PRIMARY KEY
               // Globally unique Relation identifier.

source_type    TEXT NOT NULL
               // Core concept type of the source.

source_id      UUID NOT NULL
               // ID of the source core concept.

relation_type  TEXT NOT NULL
               // Semantic meaning of the relationship.
               //
               // Examples:
               // belongs_to
               // contributes_to
               // uses
               // managed_by
               // guides
               // depends_on
               // requires
               // constrained_by
               // allocated
               // consumes
               // related_to

target_type    TEXT NOT NULL
               // Core concept type of the target.

target_id      UUID NOT NULL
               // ID of the target core concept.

metadata       JSON
               // Optional data belonging to the relationship itself.
               //
               // Especially important for Resource relations.

created_at     DATETIME NOT NULL
               // When the Relation became active.

ended_at       DATETIME
               // When the Relation stopped being active.
               // NULL means currently active.
```

No Labels, States or State Transitions are referenced through this table.

# 10. Resource Constraint Example

A Task deadline is not stored in `tasks`.

Instead:

```text

 → constrained_by
Time Resource
```

```json

  "constraint_type": "deadline",
  "value": "2026-08-20T18:00:00"
}
```

A Time allocation:

```text
Task
 → allocated
Development Time Resource
```

```json
{
  "amount": 8,
  "unit": "hour"
}
```

Actual use:

```text
Record
 → consumes
Development Time Resource
```

```json
{
  "amount": 2.5,
  "unit": "hour"
}
```

# 13. State Machine Identity

State machines are generalized around three dimensions.

Workflow template:

```text
workflow_id
+
entity_type
+
label_id
```

Project instance:

```text
project_id
+
entity_type
+
label_id
```

This allows different State Machines for different kinds of entities even when they use the same Label.

Example:

```text
Life OS
Task + Feature
    Backlog → Prototype → Implementation → Testing → Done

Life OS
Goal + Feature
    Proposed → Active → Validating → Achieved
```

# 14. `workflow_states`

Defines reusable State templates.

```text
workflow_states

id              UUID PRIMARY KEY
                // Globally unique Workflow State identifier.

workflow_id     UUID NOT NULL
                // Logical ID of the Workflow defining this machine.

entity_type     TEXT NOT NULL
                // Core entity type managed by this State Machine.
                //
                // Examples:
                // task
                // goal
                // project
                // idea
                // philosophy
                // workflow
                // resource
                // record

label_id        UUID NOT NULL
                // Label defining this State Machine variant.

title           TEXT NOT NULL
                // Human-readable State name.

description     TEXT
                // Explanation of what the State means.

category        TEXT
                // Optional normalized category useful for general UI,
                // analytics or queries.
                //
                // Examples:
                // pending
                // active
                // blocked
                // completed
                // cancelled

sort_order      INTEGER
                // Preferred visual ordering of States.

is_initial      BOOLEAN NOT NULL DEFAULT FALSE
                // Whether this is normally the initial State.

is_terminal     BOOLEAN NOT NULL DEFAULT FALSE
                // Whether this State ends this machine's lifecycle.

entry_criteria  TEXT
                // Conditions expected to be true when entering.

exit_criteria   TEXT
                // Conditions expected before leaving.

created_at      DATETIME NOT NULL
                // When the State template was created.

updated_at      DATETIME NOT NULL
                // When the State template was last modified.

archived_at     DATETIME
                // When the State template was archived.
```

Core entities do not directly enter Workflow States.

These are reusable templates.

# 15. `workflow_state_transitions`

Defines transitions inside a Workflow State Machine template.

```text
workflow_state_transitions

id                      UUID PRIMARY KEY
                        // Globally unique Transition identifier.

workflow_id             UUID NOT NULL
                        // Workflow containing the State Machine.

entity_type             TEXT NOT NULL
                        // Core entity type managed by this machine.

label_id                UUID NOT NULL
                        // Label identifying this State Machine variant.

from_state_id           UUID NOT NULL
                        // Logical ID of the source workflow_state.

to_state_id             UUID NOT NULL
                        // Logical ID of the destination workflow_state.

title                   TEXT
                        // Optional human-readable transition name.

description             TEXT
                        // Explanation of the transition.

condition               TEXT
                        // Conditions that must be satisfied before
                        // this transition may occur.

action                  TEXT
                        // Optional action/process associated with
                        // performing the transition.

requires_exit_criteria  BOOLEAN NOT NULL DEFAULT FALSE
                        // Whether the source State's exit criteria
                        // must be satisfied first.

created_at              DATETIME NOT NULL
                        // When the Transition was created.

updated_at              DATETIME NOT NULL
                        // When the Transition was last modified.

archived_at              DATETIME
                        // When the Transition was archived.
```

Application integrity rule:

```text
from_state_id
and
to_state_id
```

must reference States belonging to the same:

```text
workflow_id + entity_type + label_id
```

# 16. Project State Machine Initialization

A Project Management Workflow may initialize Project-specific State Machines.

Example:

```text
Workflow:
Software Project Management

Task + Feature:
Backlog
→ Prototype
→ Implementation
→ Testing
→ Done
```

When applied to Life OS:

```text
Workflow State Machine Template
        ↓ initialize
Life OS Project State Machine
```

The Project then owns its own machine independently.

# 19. Project State Machine Independence

A reusable Workflow may define:

```text
Task + Feature

Backlog
→ Ready
→ Implementation
→ Testing
→ Done
```

Life OS can initialize from this and later customize it:

```text
Task + Feature

Backlog
→ Defined
→ Prototype
→ UI Design
→ Ready
→ Implementation
→ Testing
→ Done
```

The Workflow template remains unchanged.

Likewise, later Workflow updates must not silently mutate the existing Project machine.

# 20. `project_entity_states`

Stores the actual State history of any core entity inside a Project.

This replaces `task_project_states`.

```text
project_entity_states

id                UUID PRIMARY KEY
                  // Globally unique identifier of this State period.

project_id        UUID NOT NULL
                  // Project management context.

entity_type       TEXT NOT NULL
                  // Core entity type being managed.
                  //
                  // Examples:
                  // task
                  // goal
                  // project
                  // workflow
                  // idea
                  // philosophy
                  // resource
                  // record

entity_id         UUID NOT NULL
                  // Logical ID of the actual core entity.

label_id          UUID NOT NULL
                  // Label identifying which Project State Machine
                  // is managing this entity.

project_state_id  UUID NOT NULL
                  // Logical ID of the actual Project State occupied.

entered_at        DATETIME NOT NULL
                  // When the entity entered this State.

ended_at          DATETIME
                  // When the entity left this State.
                  //
                  // NULL means this is the current State.

```

Current State is the active row for:

```text
project_id
+
entity_type
+
entity_id
+
label_id
```

```text
ended_at IS NULL
```

# 21. `milestones`

Stores ordered Roadmap checkpoints for one exact Project pursuit relation.

A Milestone groups descendant Goals; it is not itself a Goal, lifecycle State,
or persisted completion value. Whether it is reached is derived from the
authoritative Project execution snapshot.

```text
milestones

id                    TEXT PRIMARY KEY
                      // Globally unique Milestone identifier.

pursuit_relation_id   TEXT NOT NULL
                      // Logical reference to the exact active canonical
                      // Project -> contributes_to -> Goal relation.

title                 TEXT NOT NULL
                      // Non-blank user-facing checkpoint name.

description           TEXT
                      // Optional Milestone detail.

target_at             TEXT
                      // Optional ISO 8601 target timestamp.

sort_order            INTEGER NOT NULL CHECK (sort_order > 0)
                      // User-controlled position within the pursuit.

created_at            TEXT NOT NULL
                      // ISO 8601 creation timestamp.

updated_at            TEXT NOT NULL
                      // ISO 8601 timestamp of the last intrinsic edit.

archived_at           TEXT
                      // ISO 8601 archive timestamp.
                      // NULL means the Milestone is active.
```

Active Milestone order is unique within a pursuit. Reads are deterministic by
`sort_order`, then `created_at`, then `id`. Archiving retains the row for
historical Roadmap reads.

Indexes:

```text
milestones_pursuit_order_idx
  (pursuit_relation_id, archived_at, sort_order, created_at, id)

milestone_active_order_unique_idx UNIQUE
  (pursuit_relation_id, sort_order)
  WHERE archived_at IS NULL
```

---

# 22. `milestone_goal_assignments`

Stores ordered, temporal Goal membership within Milestones.

```text
milestone_goal_assignments

id                    TEXT PRIMARY KEY
                      // Globally unique assignment identifier.

pursuit_relation_id   TEXT NOT NULL
                      // Repeats the owning Milestone's pursuit relation for
                      // pursuit-wide uniqueness and corruption detection.

milestone_id          TEXT NOT NULL
                      // Logical reference to the owning Milestone.

goal_id               TEXT NOT NULL
                      // Logical reference to the assigned descendant Goal.

sort_order            INTEGER NOT NULL CHECK (sort_order > 0)
                      // User-controlled Goal position in the Milestone.

created_at            TEXT NOT NULL
                      // ISO 8601 assignment start timestamp.

ended_at              TEXT
                      // ISO 8601 assignment end timestamp.
                      // NULL means the assignment is active.
```

One Goal may have at most one active assignment in a pursuit. Ending an
assignment preserves it; reassigning the Goal later creates a new row.

Indexes:

```text
milestone_goal_assignments_milestone_idx
  (milestone_id, ended_at, sort_order, created_at, id)

milestone_goal_active_pursuit_unique_idx UNIQUE
  (pursuit_relation_id, goal_id)
  WHERE ended_at IS NULL
```

Neither Roadmap table has database foreign keys. The application layer checks
that the pursuit, Milestone, and Goal exist; that the assignment pursuit
matches its Milestone; and that the Goal is an active descendant of the
pursued root Goal in the same Project-scoped hierarchy.

# 24. Multiple Labels

An entity can have multiple Labels.

Example:

```text
Task: Implement Authentication

Labels:
Feature
Security
P0
Backend
```

Not every Label must define a State Machine.

For example:

```text
Feature
```

may be a management Label with a State Machine.

While:

```text
P0
Backend
```

may only be classification Labels.

This distinction is controlled by Workflow/Project configuration rather than hard-coded in the Label table.

# 25. State Transition Runtime

Suppose:

```text
Project: Life OS
Entity Type: task
Entity: Implement Goal UI
Label: Feature

Current State:
Prototype
```

Requested transition:

```text
Prototype → UI Design
```

The domain layer:

1. Resolves the current `project_entity_states` row.
2. Finds the Project State Machine using:
   `project_id + entity_type + label_id`.
3. Finds a matching `project_state_transition`.
4. Validates its conditions.
5. Validates exit criteria if required.
6. Ends the current State-history row.
7. Creates a new `project_entity_states` row.
8. Creates a Record describing what actually happened.

Example Record payload:

```json
{
  "project_id": "LIFE_OS",
  "entity_type": "task",
  "entity_id": "TASK_101",
  "label_id": "FEATURE",
  "from_project_state_id": "PROTOTYPE",
  "to_project_state_id": "UI_DESIGN"
}
```

# 26. No Foreign Keys

No table has database-level foreign keys.

Fields such as:

```text
workflow_id
project_id
label_id
entity_id
from_state_id
to_state_id
project_state_id
source_workflow_state_id
```

are logical references only.

The domain layer must validate them.

# 27. Application-Level Integrity Rules

## Entity Labels

`entity_type + entity_id` must identify an existing core concept.

`label_id` must identify an existing Label.

---

## Workflow State

`workflow_id` must identify an existing Workflow.

`label_id` must identify an existing Label.

---

## Workflow Transition

`from_state_id` and `to_state_id` must belong to the same:

```text
workflow_id
entity_type
label_id
```

---

## Project State

The State belongs to exactly one:

```text
project_id
entity_type
label_id
```

machine.

---

## Project Transition

Both States must belong to the same:

```text
project_id
entity_type
label_id
```

machine.

---

## Project Entity State

The referenced Project State must match the row's:

```text
project_id
```

# 29. Final Architecture

```text
CORE CONCEPT
Task / Goal / Project / Idea /
Philosophy / Workflow / Resource / Record
        │
        ├──────── semantic connections ───────→ relations
        │
        ├──────── classification ─────────────→ entity_labels
        ├──────── project lifecycle ──────────→ project_entity_states
        │
        └──────── Project pursuit ────────────→ milestones
                                                   │
                                                   └── milestone_goal_assignments
```

State-machine definition:

```text
Workflow
   +
Entity Type
   +
Label
   │
   ▼
Workflow State Machine Template
   │
   │ initialize
   ▼
Project
   +
Entity Type
   +
Label
   │
   ▼
Project State Machine
   │
   ▼
Core Entity Runtime State
```

Resource constraints remain orthogonal:

```text
Core Entity
    │
    ├── requires
    ├── constrained_by
    ├── allocated
    └── budgeted_by
             │
             ▼
          Resource
```

Reality remains:

```text
Something happens
      ↓
    Record
      ↓
semantic Relations
```

The final boundaries are:

**Core tables**
→ what things intrinsically are.

**`relations`**
→ semantic relationships among core concepts.

**`entity_labels`**
→ generic classification of any core concept.

**Workflow State tables**
→ reusable State Machine templates.

**Project State tables**
→ actual Project-specific State Machines.

**`project_entity_states`**
→ actual lifecycle history of core entities inside Projects.

**Roadmap Milestone tables**
→ ordered checkpoints and temporal Goal grouping for one exact Project pursuit;
completion remains derived rather than stored.

**Resources**
→ capacity and constraints.

**Records**
→ what actually happened.
